# CLAUDE.md — 《系统品酒》（books/wine）开发规范

> ⚠️ **本书是 `H-Jett/LifeLearning` 仓库中的一本**（位于 `books/wine/`），不是独立仓库。
> 仓库级约定（books.yml、统一构建、提交前缀）见根目录 [`CLAUDE.md`](../../CLAUDE.md)。
> **书内的写作纪律以本文件为准**，仓库级文件不覆盖它。

> 本文件是这本书的开发约定，Claude Code 会自动加载。人类或 AI 在此目录下开发时**必须遵守**。
> 目的：让《系统品酒：从葡萄酒到烈酒》保持统一、正确、可移植。
> 体例继承姊妹项目 TeaLearning / JewelryLearning / CoffeeLearning。

## 0. 法律与健康的前置声明（写任何一章都适用）

- 本书面向**法定饮酒年龄以上**的读者。每章涉及实际饮用的实操，都要带一句
  **「适度饮酒，未成年人不饮酒，酒后不驾车」**，一句即可，不展开劝诫。
- **不做医疗与健康建议**。"红酒软化血管""白藜芦醇抗癌""适量饮酒延寿"这类说法，
  只陈述**研究现状与证据等级**（观察性研究 / RCT / 孟德尔随机化 / 系统综述），
  不给剂量、不给疗效承诺、不做"该不该喝"的结论。相关内容集中在第七部分。
- **不写具体购买渠道与代购信息**，不做投资建议（酒类投资、期酒、名庄涨幅）。
  价格只讲**定价机制与相对结构**。

## 1. 这是什么

一本"边学边记"的品酒入门书，**双目标**：

1. **实用**：能读懂酒标、能把风味说清楚、能判断一瓶酒值不值这个价、会侍酒与配餐；
2. **系统**：从**物质基础 → 品种与风土 → 工艺 → 产区法规 → 系统品鉴 → 烈酒**建立完整框架，
   覆盖葡萄酒之外的蒸馏酒（威士忌 / 白兰地 / 朗姆 / 龙舌兰 / 金酒 / 中国白酒）。

面向零基础但要求讲透原理的读者。最终会成书，所以：

> **⚠️ 内容必须非常正确。**

姊妹书 InfraLearning 靠"真机跑数据"自证；酒没有 GPU 可跑，**本书的正确性靠四条纪律**：

1. **数值必须有出处**：残糖、总酸、pH、酒精度、单宁含量、香气阈值、法定产量上限、
   陈年月数等，一律标注来源（OIV / EU 法规 / 产区 cahier des charges 与 disciplinare /
   TTB 27 CFR / GB/T 国标 / 同行评议论文 / 权威教材），并给**区间**而非单点。
   **禁止凭印象编造精确数字**——宁可写"典型在 x~y，因年份与产区差异很大"。
2. **区分「事实」「法规规定」「行业惯例」「酒圈传说」**四层：
   - **事实**：物理化学与生理学，可验证、可复现；
   - **法规规定**：法规/标准怎么写的（引编号，登记进 `docs/standards.md`）；
   - **行业惯例**：行业怎么做、怎么叫、怎么定价（明说是惯例，可能变）；
   - **传说**：酒圈流传的说法。凡证据不足的，一律进「常见说法辨析」小节，
     标注**证据强度**（✅ 有共识 / ⚠️ 有争议 / ❌ 明确错误 / 缺乏证据），不含糊其辞。
3. **价格只讲机制，不写死数字**：汇率、关税、年份行情随时变。正文写**定价逻辑与相对关系**，
   需要绝对数字时标注"截至 YYYY-MM 的量级，仅供理解结构"。
4. **不做鉴定与真伪结论**：隔着屏幕不能判断一瓶酒的真伪与品质；本书教怎么看、怎么问、
   怎么用可复现的方法自己验证。

**版权红线（本书特有，务必记住）**：

- **WSET 的 SAT（Systematic Approach to Tasting）是 WSET 的版权材料**——
  **不得照抄它的条目表述、词汇分层与表格版式**，也不要把本书的品鉴表做成它的等价物。
  本书自拟品鉴结构，需要提到时写"参考公开发表的系统性品鉴框架"，并引用**可公开引用**的来源
  （OIV 国际评酒会评分表、ISO 3591 品酒杯标准、Davis 20 分制等，登记进 `docs/standards.md`）。
- 同理**不搬运他人实拍图与酒标扫描图**（酒标含商标）。要图就用 Mermaid 或纯文字判据，
  必要时在正文里**给权威图库/官网链接**（不下载、不热链）。
- 香气轮盘（如 Ann Noble 的 Wine Aroma Wheel）等图形**有版权**，只给链接，不复制图形与条目表。

### 1.1 查证纪律（硬要求，写每一章都适用）

> **不要凭记忆写作。** 姊妹书 InfraLearning 有真机数据可跑，酒没有——
> **所以"查资料"是本书正确性的唯一来源**，不是可选项。
> 酒更是个话术密度极高的行业：模型记忆里混进了大量销售话术、自媒体误传与过期法规。

1. **写之前先查**：动笔前检索**一手资料**（OIV 文件与分析方法汇编、EU 法规原文、
   各产区法规原文、TTB 27 CFR、GB/T 国标原文、*Wine Science*（Jackson）、
   *Understanding Wine Chemistry*（Waterhouse 等）、*The Oxford Companion to Wine*、
   AWRI 技术资料、*Am. J. Enol. Vitic.* 等同行评议文献），而不是凭印象组织内容。
   **先列出本章每个数值与每条判据的来源，再开始写**。
2. **一手优先，来源分级**：法规与标准原文 / 官方统计（OIV、各国监管机构）/ 同行评议论文 /
   权威教材 > 产区管理机构与科研机构（INAO、BNIC、CRT、AWRI、UC Davis）科普 >
   头部专业媒体（JancisRobinson.com、Decanter、Wine Business）> 酒商内容 > 自媒体与直播话术。
   **酒商文案与自媒体一律不作依据**，只能当"市场上存在这种说法"的证据（正是辨析小节的素材）。
3. **关键结论交叉验证**：成分含量、感知阈值、法定限值、工艺参数、陈年要求，
   至少**两个独立来源**一致才写；只有一个来源时明确写"仅见于 X"。
4. **查不到就别写死数字**：宁可写"这一点缺乏可靠公开数据"，或改成**写规律 / 标"经验值"
   并说明波动范围**。**绝不用听起来合理的措辞填补空白**。发现自己在"推测"时，
   停下来去查，或显式标注为推测。
5. **出处要落盘**：所有引用登记进 [`docs/standards.md`](docs/standards.md)
   （`check_book.py` 会强制：正文出现的 GB/T 编号、EU 法规号、ISO 编号、NOM 编号必须已登记）。
6. **凡话术必辨析**：酒圈说法一律进「常见说法辨析」小节，标注证据强度，
   并说明它为什么流传、卖家为什么爱说。
7. **警惕自己的记忆**：法规改版极频繁（EU 2021/2117 加了脱醇酒类别、
   TTB 27 CFR Part 5 在 2022 年大改、GB/T 15109 重新定义了白酒、干邑 XO 的最低陈年年数改过、
   德国酒法 2021 年改革），**默认记忆已经过期，一律现查现标**。
8. **各国规则不一致时并列**：朗姆酒没有全球统一定义、"甜度"术语 EU 与中国国标不同、
   "威士忌"的拼写与定义各国有别——**不要把一方当成唯一正确**，并列说明，
   指出读者在中国市场与海外市场分别会看到什么。
9. **感官结论要写清"谁的感知"**：阈值、偏好、"平衡"都有巨大个体差异（含遗传因素）。
   写阈值必须给测定条件（介质、人群、方法），不要写成绝对常数。

## 2. 教学法（每章固定结构）

用**中文**写。每章遵循「**概念 → 辨析 → 思考题 → 实操 → 用处**」，顺序固定：

1. **概念正文**：配机理图（Mermaid）/ 对照表，关键数值带出处；能讲"为什么"就不要只讲"是什么"；
2. **「常见说法辨析」表**：逐条标证据强度 ✅ 有共识 / ⚠️ 有争议 / ❌ 明确错误 / 缺乏证据；
3. **「思考题」**（数量**按内容而定，不固定**），紧扣本章，指向答案册（见 §5）。题型混用：
   - 普通问答（考原理）；
   - **【案例】判断题**：给一段真实感的酒标 / 酒评 / 报价 / 直播话术，问"说得对不对、坑在哪"，
     答案册必须给**完整推理链**；
   - **【查证】题**：让读者自己去查法规原文或数据库，体会"一手资料长什么样"。
4. **「本章实操」**，两档（读者手上**不一定有酒**，而且**不应该为了做题去喝酒**）：
   - **🅐 无器具版**：现在就能做，且**不需要开瓶喝酒**——读酒标把法规术语翻译成信息、
     查某个产区法规的产量上限/最低酒精度、比对两张酒评的用词、算糖酒转化；
   - **🅑 有条件版**：标注**「备齐后再做」**，列清所需**酒款与器具**（杯型、温度计、
     真空塞、记录表），并写明"适度饮酒"。
   实操要给**可填写的记录表**（Markdown 表格或链到 `docs/forms/`）。
5. **🔎「买酒与点酒时的用处」**：把本章原理压缩成几个可执行动作。**每章必有**。

风格：像给同事讲清楚一件事，多用"为什么"，诚实标注反直觉与局限（"诚实说明"）。
**绝不写"这瓶酒一定是假的/一定不好"这类隔屏断言**——写"出现这些特征时，怀疑 X，需要 Y 来确认"。

## 3. 单一真源 & 可移植 Markdown（核心原则）

- **内容只存一份**：正文 `docs/`。网页 / PDF 都是它的渲染。
- **可移植 Markdown**：必须在 **GitHub 原生渲染 + 普通 Markdown 阅读器 + MkDocs** 三边都能看：
  - 用**脚注 + 引用块**做注释，**不要**用 MkDocs 专有的 `!!! note` admonition；
  - 术语表锚点、思考题跳转都用**显式 HTML 锚点** `<a id="xxx"></a>`（三边通用）；
  - 不用 `--8<--` / `{{#include}}` 这类构建期引用（纯阅读器看不到）。
- **禁止绝对路径**（公开仓库会泄漏个人信息与目录布局）；站内链接用相对路径 `.md#anchor`，
  **锚点必须真实存在**（`check_book.py` 会查）。
- **可复用的表单**（品鉴记录表、酒标核对清单、酒柜清单等）放 `docs/forms/`，
  各章**链接**过去，不复制粘贴。

七个部分的目录名固定为：

`03-winemaking`（酿造与陈年）、`04-regions`（产区与酒标法规）、

## 5. 各类文件的具体约定

**章节 `.md`**：小节用 `## N.x 标题`。术语首次出现加脚注 `[^x]`，脚注体链接到术语表
`[术语](../../glossary.md#anchor)`。章末思考题下写跳转链接：
`> 📖 **参考答案**（想清楚再看）：[Q1](../../qa/NN-name-qa.md#q1) · [Q2](...#q2) · …`

**答案册 `docs/qa/NN-name-qa.md`**：**只记「问题 + 正确答案」**，不记读者作答。
每题前加锚点 `<a id="q1"></a>`…。案例题答案要给推理链（"看到什么 → 推出什么 → 还需要确认什么"）。
必须加进 `mkdocs.yml` 的「思考题参考答案」nav（否则 `--strict` 报错）。

**出处标注格式**：

- 中国国标写编号**不带年份**（`GB/T 15037`），在 `standards.md` 登记完整名称与当前版本，
  注明"以最新发布版本为准"——年份写进正文会随改版失效。
  ⚠️ 但**当某次改版本身是知识点时**（如白酒定义的变化），在正文里明确写"某年修订起"。
- EU 法规写 `(EU) 2019/787` 这种规范形式；美国联邦法规写 `27 CFR 5`（章节号在脚注里给）。
- 教材引用统一简称（如《Wine Science》《Understanding Wine Chemistry》
  《The Oxford Companion to Wine》），同样在 `standards.md` 登记。
- 行业惯例写明"**行业惯例**，可能随行情变化"；经验值写明"**经验值**，不同资料略有差异"。

**术语表**：新术语加到 `glossary.md` 对应主题下，前置 `<a id="slug"></a>`。
酒类术语要给 **中文 + 原文术语（法/意/西/德文，若有）+ 英文**——
因为酒标和报告多是外文，读者必须能对上。`## ` 节号不得重复（写完 `grep '^## '` 自查）。

## 6. 实战项目（重要：不要一章一个）

- 项目**只挂在部分末尾**，同一部分**最多一个**，全书 **5 个**（P1~P5）。
- 项目文档放**所属部分目录**里（`chapters/NN-part/project-PN-xxx.md`），
  nav 排在该部分末尾，**不单独设分区**。
- 项目同样给「🅐 无器具版 / 🅑 有条件版」两档，并给交付物模板（表格 / 决策清单）。
- 🅐 档同样**不要求开瓶喝酒**：读法规、读酒标、查数据库、做方案都可以是交付物。

## 7. 画图（Mermaid 优先）

> **随时画图**：只要图比文字更清楚，就配图——这是硬要求，别偷懒用纯文字凑。

- **分类树 / 判定流程 / 工艺流程 / 成分—感受对应 / 决策树 → Mermaid**：用 mermaid 围栏代码块，
  三边都渲染、可 diff。本书最常用：成分→感受映射图、酿造工序图、产区层级树、
  酒标读取流程、蒸馏器示意、缺陷排查决策树。
- **数据图表**：**只在有可靠数据来源时才画**，图注必须写来源；没有来源就不要画成
  "像实测数据"的样子，改用示意图并在标题里写明"示意"。
  ⚠️ **不要用 matplotlib 画带中文的图**：本机没有中文字体，会变方框。
  需要静态图时写 SVG（文字由读者浏览器渲染）。
- **颜色描述**：涉及酒色的图/表不要只靠色块传达信息（色盲不友好且屏幕色差大），
  必须同时给**文字描述**（色调 / 深浅 / 边缘色带）。
- **地图不要自绘**：产区地理关系用 Mermaid 的层级/邻接关系表达，或给权威地图链接。

## 8. 新增一章的标准流程（照做）

1. 先列本章的知识链条，**为每个数值与判据找到出处**（查不到就改写法，别编）；
2. 写 `docs/chapters/PART/NN-name.md`（概念 + Mermaid/表 + 常见说法辨析 + 思考题 +
   本章实操 🅐/🅑 + 🔎 用处）；
3. 写 `docs/qa/NN-name-qa.md`（问题 + 正确答案，`q1`/`q2`/… 锚点；案例题给推理链）；
4. 新术语加进 `glossary.md`，新出处加进 `standards.md`（标核对状态）；
5. 更新 `mkdocs.yml`（章节 nav + 答案 nav）、`docs/index.md`（进度）、
   `docs/roadmap.md`（状态）；
6. **校验 + 严格构建**（见 §9）全绿后再提交。

## 9. 构建与校验（提交前必做）

```bash
python scripts/check_book.py     # 锚点/出处登记/绝对路径/admonition/章节结构/健康措辞
mkdocs build --strict            # 坏链接或警告即失败（CI 也跑这条）
```

在仓库根上只构建本书（**必须带 `--only wine`**，不带会清空整个 `site/`）：

```bash
python scripts/build_site.py --only wine
```

两条全过才提交。`--strict` 失败会导致 GitHub Actions 部署失败、网页冻结——务必本地先过。

## 10. 提交与发布

- 提交信息中文、说清做了什么 + 为什么；**每完成一块可独立成立的内容就提交**，不要攒到最后。
- 提交信息加书名前缀，如 `wine: 第 3 章 酒精发酵的化学`（见根 CLAUDE.md §6）。
- push 到 `main` 触发**仓库级** workflow（构建全部书）并发布到 GitHub Pages。

## 11. 通用约束（来自用户全局规范）
