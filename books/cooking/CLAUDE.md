# CLAUDE.md — 《做菜的原理》（books/cooking）开发规范

> ⚠️ **本书是 `H-Jett/LifeLearning` 仓库中的一本**（位于 `books/cooking/`），不是独立仓库。
> 仓库级约定（books.yml、统一构建、提交前缀）见根目录 [`CLAUDE.md`](../../CLAUDE.md)。
> **书内的写作纪律以本文件为准**，仓库级文件不覆盖它。

> 本文件是这本书的开发约定，Claude Code 会自动加载。人类或 AI 在此目录下开发时**必须遵守**。
> 目的：让这本《做菜的原理：从照着菜谱做到自己决定怎么做》保持统一、正确、可移植。
> 体例继承姊妹书 TeaLearning / JewelryLearning / CoffeeLearning。

## 1. 这是什么

一本写给**厨房小白**的原理书。读者的痛点不是"没有菜谱"，而是
**菜谱只说做什么、不说为什么**：为什么要焯水？为什么先炒蛋再炒番茄？
为什么这里加料酒、那里加糖？盐什么时候放？

所以本书的**唯一目标**是：

> **让读者下次做一道没做过的菜时，自己知道该怎么处理食材、加什么、按什么顺序。**

由此推出两条硬性写作要求：

1. **每一章都要回答"为什么"**，并给出**可迁移的判断规则**——
   读者要能把这一章的原理套到菜谱之外的新情况上；
2. **不罗列菜谱**。第六部分虽然拆解家常菜，但每一步都必须标注它对应前面哪条原理，
   并给"变体推演"（换食材、换设备该怎么调），否则就退化成菜谱书了。

全书的解释框架是**四条线**：**热 · 水 · 味 · 时间**。任何一步操作都要能归到其中一条
（第 1 章建立这个框架，后面六部分分别服务它）。

最终会成书，所以：

> **⚠️ 内容必须非常正确。**

姊妹书 InfraLearning 靠"真机跑数据"保证正确性；做菜没有 GPU 可跑，而厨房恰恰是
**谣言密度最高的地方**（"锁住肉汁""热锅冷油""味精有害"），**本书的正确性靠四条纪律**：

1. **数值必须有出处**：温度、时间、浓度、损失率等数字，一律标注来源
   （各国食品安全机构指引 / 同行评议文献 / 权威著作与教材），并给**区间**而非单点。
   **禁止凭印象编造精确数字**——宁可写"典型在 x~y，随食材/锅具/火力差异很大"，
   或者干脆**只写规律不写数字**。
2. **区分「事实」「官方规定」「行业/家庭惯例」「厨房传说」**四层：
   - **事实**：可测量、可复现的物理化学现象（水在常压下 100 °C 沸腾、蛋白质受热变性）；
   - **官方规定**：食品安全机构的公开指引怎么写的（引机构名 + 页面主题，并注明各国口径不同）；
   - **惯例**：餐馆与家庭怎么做（明说是惯例，可能只在特定条件下成立）；
   - **厨房传说**：流传的说法。凡证据不足的，一律写进「常见说法辨析」小节，
     标注**证据强度**（✅ 有共识 / ⚠️ 有争议 / ❌ 明确错误 / 缺乏证据），不含糊其辞。
3. **食品安全的数字必须引官方来源**：肉类中心温度、危险温度带、放置时间限制，
   一律引各国食品安全机构的公开指引（美国 FDA / CDC、加拿大卫生部、英国 FSA、WHO 等），
   **并明确写出不同国家口径不同**——不要把某一国的数字当成唯一正确答案。
4. **不做医疗 / 营养治疗建议**：营养相关**只讲证据等级**
   （谁做的研究、什么设计、机构结论的原话与适用范围），
   **不给摄入量建议、不做疗效或风险承诺**。

### 1.1 查证纪律（硬要求，写每一章都适用）

> **不要凭记忆写作。** 姊妹书 InfraLearning 有真机数据可跑，做菜没有——
> **所以"查资料"是本书正确性的唯一来源**，不是可选项。
> 厨艺更是个"经验先行、科学解释后到"的领域：模型记忆里混进了大量
> 菜谱套话、短视频结论与厨师口传，其中一部分是错的，另一部分只是**尚未被验证**。

1. **写之前先查**：动笔前检索**一手资料**（各国食品安全机构的官方页面、
   同行评议文献、权威著作如 McGee《On Food and Cooking》、
   López-Alt《The Food Lab》、Myhrvold 等《Modernist Cuisine》、
   Nosrat《Salt, Fat, Acid, Heat》、Corriher《CookWise》、This《Molecular Gastronomy》、
   America's Test Kitchen《The Science of Good Cooking》，以及中式烹饪职业教育教材），
   而不是凭印象组织内容。**先列出本章每个数值与每条判据的来源，再开始写**。
2. **一手优先，来源分级**：官方食品安全指引 / 同行评议论文 / 权威著作与教材 >
   有公开方法与数据的实验型作者（如 Serious Eats 的对照实验报道、
   Cook's Illustrated / America's Test Kitchen 的实验结论）>
   专业媒体 > 厨具与调料厂商内容 > 菜谱站与短视频。
   **厂商内容与短视频一律不作依据**，只能当"厨房里存在这种说法"的证据
   （正是「常见说法辨析」小节的素材）。
3. **关键结论交叉验证**：温度阈值、时间、损失率、安全红线，至少**两个独立来源**一致才写；
   只有一个来源时明确标注"仅见于 X"。
4. **出处要落盘**：所有引用登记进 [`docs/standards.md`](docs/standards.md)
   （参考书目与出处登记，含 ✅ 已核对 / ⚠️ 待核对 状态），
   并且**每章末尾必须有「本章依据」小节**，列出这一章用到的书与具体章节/页码范围
   （`scripts/check_book.py` 会检查这个小节存在）。
5. **查不到就别写死数字**：宁可写"这一点缺乏可靠公开数据"，或改成
   **规律描述 + 标注"经验值"并说明波动范围**，**绝不用听起来合理的措辞填补空白**。
   发现自己在"推测"时，停下来去查，或**显式标注为机制推理**。
   ⚠️ 已知的典型陷阱：很多流传很广的厨房数字（例如"美拉德反应从 140~165 °C 开始"）
   在二手资料里到处出现，但**找不到可靠的一手实验出处**——这类数字要么标明来源薄弱，
   要么改写成方向性规律。
6. **凡说法必辨析**：厨房说法一律进「常见说法辨析」小节，标注证据强度，
   并说明它**为什么流传**（通常是因为在某个特定场景下确实成立，被过度推广了）。
7. **警惕自己的记忆**：各国安全温度的当前口径、某本书的版次与页码、
   某个实验到底测了什么，**默认记忆已经过期**，一律现查。
8. **只复述，不抄原文**：**不得**整段翻译或改写他人文字，**不得**搬运他人的图片与表格版式。
   表格必须是自己按本书需要重新组织的；引用他人实验时复述**结论与方法**，不复制表述。

## 2. 教学法（每章固定结构）

用**中文**写。每章顺序固定为「**概念 → 辨析 → 思考题 → 实操 → 用处 → 依据**」
（`scripts/check_book.py` 会检查小节是否齐全）：

1. **概念**讲解，配机理图（Mermaid）/ 对照表，关键数值带出处；
   **能讲"为什么"就不要只讲"是什么"**；每章结束前要把原理收敛成**一条可迁移的判断规则**。
2. **「常见说法辨析」**表：逐条列出厨房里流传的说法，标注证据强度
   （✅ 有共识 / ⚠️ 有争议 / ❌ 明确错误 / 缺乏证据）并给一句理由。
3. 章末**思考题**（数量**按内容而定，不固定 3 道**），紧扣本章，指向答案册（见 §5）。
   题型混用：
   - 普通问答（考原理）；
   - **【案例】题**：给一个**新食材 / 新情境 / 一段菜谱**，让读者**自己推处理方案**，
     答案册必须给**完整推理链**（"目标是什么 → 哪条线是主要手段 → 顺序怎么定"）；
   - **【辨析】题**：给一条流传的说法，让读者判断证据强度并说明怎么验证。
4. **本章实操**，两档：
   - **🅐 零成本版**——**不用开火**就能做（把一份菜谱逐行翻译成原理、
     配不同浓度的盐水找自己的咸度阈值、看自己冰箱里的食材做处理方案表）；
   - **🅑 开火版**——标注"**有灶台和食材时做**"，给**可控变量的小对照实验**
     （同样的蛋分别用冷锅/热锅炒，记录差别），并列清所需器具与替代方案。
   实操要给**可填写的记录表**（Markdown 表格或链到 [`docs/forms/`](docs/forms/)）。
5. **🔎「下次做菜时的用处」**：把本章原理翻译成**当场少犯的那一个错**。
6. **「本章依据」**：本章用到的书/论文/官方页面 + 具体章节或页码范围。

风格：像给同事讲清楚一件事，多用"为什么"，诚实标注反直觉与局限（"诚实说明"）。
**绝不写"这么做一定不好吃"这类绝对断言**——写"出现 X 时，先怀疑 Y，用 Z 来验证"。

## 3. 单一真源 & 可移植 Markdown（核心原则）

- **内容只存一份**：正文 `docs/`。网页/PDF 都是它的渲染。
- **可移植 Markdown**：必须在 **GitHub 原生渲染 + 普通 Markdown 阅读器 + MkDocs** 三边都能看：
  - 用**脚注 + 引用块**做注释，**不要**用 MkDocs 专有的 `!!! note` admonition；
  - 术语表锚点、思考题跳转都用**显式 HTML 锚点** `<a id="xxx"></a>`（三边通用）；
  - 不用 `--8<--` / `{{#include}}` 这类构建期引用（纯阅读器看不到）；
  - 站内链接用相对路径 `xxx.md#anchor`，**锚点必须真实存在**（校验脚本会查）。
- **可复用的表单**（一道菜的处理方案表、尝味纠偏表等）放 `docs/forms/`，
  各章**链接**过去，不复制粘贴。
- **图片版权**：本书**不搬运**他人照片，也不内嵌外链图片。
  要看实物时，正文给**文字判据**（"应该看到什么、听到什么、闻到什么"）。
  自绘示意图用 Mermaid。

```

  roadmap.md                   # 七部分学习路线图（活的大纲，改动记进"调整记录"）
  glossary.md                  # 术语表（中文 + 英文 + 解释，每词条前有 <a id> 锚点）
  standards.md                 # 参考书目与出处登记（书/论文/官方页面 + 核对状态）
  forms/                       # 可复用记录表
    index.md
    dish-plan.md               # 一道菜的处理方案表（全书核心工具）
    tasting-fix.md             # 尝味纠偏表
  chapters/NN-partname/        # 每部分一个目录
    00-intro.md                # 该部分开篇导读（每部分都要有）
    NN-name.md                 # 章节，两位数字前缀（全书连续编号）
    summary.md                 # 该部分小结（速查，可选）
```

## 5. 各类文件的具体约定

**章节 `.md`**：小节用 `## N.x 标题`。术语首次出现加脚注 `[^x]`，脚注体链接到术语表
`[术语](../../glossary.md#anchor)`。章末思考题下写跳转链接：
`> 📖 **参考答案**（想清楚再看）：[Q1](../../qa/NN-name-qa.md#q1) · [Q2](...#q2) · …`

**答案册 `docs/qa/NN-name-qa.md`**：**只记「问题 + 正确答案」**，不记读者作答。每题前加锚点
`<a id="q1"></a>`…。案例题答案要给推理链（"目标 → 主要手段 → 约束 → 顺序 → 怎么验证"）。
必须加进 `mkdocs.yml` 的「思考题参考答案」nav（否则 `--strict` 报错）。

**出处标注格式**：正文引用著作用统一简称（如 McGee《On Food and Cooking》、
《The Food Lab》、《Modernist Cuisine》），并在 `docs/standards.md` 登记
完整书名、作者、版次、对应主题与**核对状态**（✅ 已核对到一手 / ⚠️ 待核对）。
引用官方指引时写机构名 + 页面主题（如"美国 CDC 的食品安全页面"），
**并注明"各国口径不同，以当地现行发布为准"**。标准编号（若出现 `GB xxxxx` / `ISO xxxx`）
必须在 `standards.md` 登记过，校验脚本会查。

**术语表**：新术语加到 `glossary.md` 对应主题下，前置 `<a id="slug"></a>`。
术语要给 **中文 + 英文原词**（很多资料是英文，读者要能对上），
中式术语再给一句"它在厨房里具体指什么动作"。
`## ` 节标题不许重复（校验脚本会查，重复会让自动锚点相互覆盖）。

## 6. 实战项目（重要：不要一章一个）

- 项目**只挂在部分末尾**，同一部分**最多一个**，全书 **5 个**（P1~P5）。
- 项目文档放**所属部分目录**里（`chapters/NN-part/project-PN-xxx.md`），
  nav 排在该部分末尾，**不单独设分区**。
- 项目同样给「🅐 零成本版 / 🅑 开火版」两档，并给交付物模板（表格 / 决策清单）。

## 7. 画图（Mermaid 优先）

> **随时画图**：只要图比文字更清楚，就配图——这是硬要求，别偷懒用纯文字凑。

- **传热路径 / 反应链 / 工艺顺序 / 判断决策树 → Mermaid**：```mermaid 代码块，
  三边都渲染、可 diff。本书最常用：四条线的归类图、一道菜的时序图、
  失败现象→原因的排查树、温度轴上的"谁在什么温度发生什么"。
- **没有可靠数据来源的量化关系，不要画成"像实测数据"的图**；
  必须画时在标题里写明「示意」，并在图注说明这是定性关系。
- **不要用 matplotlib 画带中文的图**：本机没有中文字体，中文会变方框。
  需要静态图时优先 Mermaid，或写成表格。
- **温度轴图**要标明"这些阈值随体系（含水量、盐、pH、升温速率）漂移"，不要画成硬边界。

## 8. 新增一章的标准流程（照做）

1. 先列本章的知识链条，**确认每个数值有出处**（查不到就改写法，别编）；
2. 写 `docs/chapters/PART/NN-name.md`
   （概念 + Mermaid/表 + 常见说法辨析 + 思考题 + 本章实操 🅐/🅑 + 🔎 + 本章依据）；
3. 写 `docs/qa/NN-name-qa.md`（问题 + 正确答案，q1/q2/… 锚点；案例题给推理链）；
4. 新术语加进 `glossary.md`，新出处加进 `standards.md`，新表格加进 `forms/`；
5. 更新 `mkdocs.yml`（章节 nav + 答案 nav）、`docs/index.md`（进度）、
   `docs/roadmap.md`（状态）；
6. **校验 + 严格构建**（见 §9）全绿后再提交。

## 9. 构建与校验（提交前必做）

```bash
python scripts/check_book.py     # 锚点 / 出处登记 / 绝对路径 / admonition / 章节结构
mkdocs build --strict            # 坏链接或警告即失败（CI 也跑这条）
```

两条全过才提交。仓库级构建（会顺带下发配色与 PWA 生成物）：

```bash
python ../../scripts/build_site.py --only cooking
```

⚠️ `docs/assets/palette.css`、`docs/assets/favicon.svg`、`overrides/main.html`
**由 books.yml 下发生成，不要手写、不要手改**。
⚠️ 多人/多 agent 并行时**只能带 `--only cooking`**，不带 `--only` 会清空整个 `site/`。

## 10. 提交与发布

- 提交信息中文、说清做了什么 + 为什么；**每完成一块可独立成立的内容就提交**，不要攒到最后。
- push 到 `main` 触发**仓库级** workflow（构建全部书）并发布到 GitHub Pages；
  提交信息加书名前缀，如 `cooking: 第 3 章 水`（见根 CLAUDE.md §6）。
- `mkdocs.yml` 配 `site_url` + `repo_url` + `repo_name`；`README.md` 顶部放**在线阅读**链接——
  网页与仓库互相可达。

## 11. 通用约束（来自用户全局规范）

- **不主动写报告文件**（`*.md` 总结、`report_*.json` 等）；结论直接说，除非明确要求导出。
- 需要时间戳用**北京时间**：`TZ='Asia/Shanghai' date '+%Y-%m-%d %H:%M'`。
- **仓库内所有文件禁止出现绝对路径**（尤其带用户名或机器目录布局的）——公开仓库会泄漏个人信息；
  只用相对路径 / 环境变量。聊天里为方便定位可给绝对路径，但**绝不提交进仓库**。
