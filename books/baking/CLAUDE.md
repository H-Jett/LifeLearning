# CLAUDE.md — 《烘焙的原理》（books/baking）开发规范

> ⚠️ **本书是 `H-Jett/LifeLearning` 仓库中的一本**（位于 `books/baking/`），不是独立仓库。
> 仓库级约定（books.yml、统一构建、提交前缀）见根目录 [`CLAUDE.md`](../../CLAUDE.md)。
> **书内的写作纪律以本文件为准**，仓库级文件不覆盖它。

> 本文件是这本书的开发约定，Claude Code 会自动加载。人类或 AI 在此目录下开发时**必须遵守**。
> 目的：让这本《烘焙的原理：从看懂配方到自己改配方》保持统一、正确、可移植。
> 体例继承姊妹书 TeaLearning / JewelryLearning / CoffeeLearning /《做菜的原理》。

## 1. 这是什么

一本写给**厨房小白**的原理书。读者的痛点不是"没有配方"，而是
**配方只说放多少、不说为什么是这个量**：为什么这份饼干放 60 g 糖？
糖少放一半会怎样？黄油换成油行不行？高筋粉能不能做蛋糕？

烘焙和炒菜的根本差别，正是这本书的立足点：

> **炒菜可以边尝边改，烘焙一旦进炉就改不了。**
> 所有决定都在配方与操作里**提前做完**，进炉之后你只能看着。

所以本书的**唯一目标**是：

> **让读者看懂一份配方里每样东西在干什么、每个比例意味着什么、
> 改动一处会连带改动什么——最终能自己改配方。**

由此推出三条硬性写作要求：

1. **每一章都要回答"为什么"**，并给出**可迁移的判断规则**——
   读者要能把这一章的原理套到配方之外的新情况上；
2. **不罗列配方**。第六部分虽然逐类拆解成品，但每一步都必须标注它对应前面哪条原理，
   并给「**变体推演**」（换糖量 / 换油脂 / 换粉 / 减糖 / 放大份量分别会发生什么），
   否则就退化成配方书了；
3. **凡出现配方与比例，一律用[烘焙百分比](docs/glossary.md#bakers-percentage)表达，
   并写明以何物为 100%**（`scripts/check_book.py` 会查）。
   烘焙百分比是本书的通用语言：它让不同来源的配方**可比较、可缩放、可改**。

全书的解释框架是**竞争关系的配平**：一份配方里的原料在**争同一批资源**——
争水、争面筋、争温度窗口、争气。改任何一项都是在改配平，所以每次改动都要问：
**"它会抢走谁的什么？"**（第 1 章建立这个框架，后面六部分分别服务它。）

最终会成书，所以：

> **⚠️ 内容必须非常正确。**

烘焙是**谣言密度极高**的领域（"必须揉出手套膜""戚风塌了一定是没倒扣"
"泡打粉和小苏打可以互换"），而且**读者没法当场纠错**——一炉毁了就是毁了。
**本书的正确性靠四条纪律**：

1. **数值必须有出处**：温度、时间、比例、含水量、损失率等数字，一律标注来源
   （同行评议文献 / 权威著作与教材 / 各国食品安全机构指引），并给**区间**而非单点。
   **禁止凭印象编造精确数字**——宁可写"典型在 x~y，随面粉、烤箱与配方差异很大"，
   或者干脆**只写规律不写数字**。
2. **区分「事实」「官方规定」「行业惯例」「烘焙传说」**四层：
   - **事实**：可测量、可复现的物理化学现象（淀粉在有水受热时糊化、碳酸氢钠遇酸产生 CO₂）；
   - **官方规定**：食品安全机构的公开指引怎么写的（引机构名 + 页面主题，并注明各国口径不同）；
   - **惯例**：烘焙坊与家庭怎么做（明说是惯例，可能只在特定条件下成立）；
   - **烘焙传说**：流传的说法。凡证据不足的，一律写进「常见说法辨析」小节，
     标注**证据强度**（✅ 有共识 / ⚠️ 有争议 / ❌ 明确错误 / 缺乏证据），不含糊其辞。
3. **食品安全的数字必须引官方来源**：生面糊与生面粉、生蛋、天然酵种、保存期限，
   一律引各国食品安全机构的公开指引（美国 FDA / CDC、英国 FSA、WHO 等），
   **并明确写出不同国家口径不同**。
4. **不做医疗 / 营养治疗建议**：**无麸质只讲工艺与代价，不谈治疗**；
   减糖、减油只讲它在配方里抢走了什么，不给摄入量建议、不做疗效承诺。

### 1.1 查证纪律（硬要求，写每一章都适用）

> **不要凭记忆写作。** 烘焙是"工艺先行、科学解释后到"的领域：
> 模型记忆里混进了大量配方套话、短视频结论与烘焙师口传，其中一部分是错的，
> 另一部分只是**尚未被验证**。

1. **写之前先查**：动笔前检索**一手资料**（同行评议文献、权威著作与教材，
   见 [`docs/standards.md`](docs/standards.md)），而不是凭印象组织内容。
   **先列出本章每个数值与每条判据的来源，再开始写**。
2. **一手优先，来源分级**：同行评议论文 / 官方食品安全指引 / 职业烘焙教材与权威著作 >
   有公开方法与数据的实验型来源（America's Test Kitchen、Serious Eats 的对照实验报道）>
   专业媒体 > 原料与设备厂商内容 > 配方站与短视频。
   **厂商内容与短视频一律不作依据**，只能当"存在这种说法"的证据
   （正是「常见说法辨析」小节的素材）。
3. **关键结论交叉验证**：温度阈值、比例、含水量、安全红线，至少**两个独立来源**一致才写；
   只有一个来源时明确标注"仅见于 X"。
4. **出处要落盘**：所有引用登记进 [`docs/standards.md`](docs/standards.md)
   （参考书目与出处登记，含 ✅ 已核到一手 / ⚠️ 待核 状态），
   并且**每章末尾必须有「本章依据」小节**，列出这一章用到的书与具体主题/页码范围
   （`scripts/check_book.py` 会检查这个小节存在）。
5. **查不到就别写死数字**：宁可写"这一点缺乏可靠公开数据"，或改成
   **规律描述 + 标注"经验值"并说明波动范围**，**绝不用听起来合理的措辞填补空白**。
   发现自己在"推测"时，停下来去查，或**显式标注为机制推理**。
   ⚠️ 已知陷阱：烘焙圈流传的很多精确数字（各种"黄金比例"、"面团必须打到 26 °C"、
   "美拉德反应从 140~165 °C 开始"）在二手资料里到处出现，但**找不到可靠的一手实验出处**。
6. **凡说法必辨析**：烘焙说法一律进「常见说法辨析」小节，标注证据强度，
   并说明它**为什么流传**（通常是因为在某类配方里确实成立，被过度推广到所有配方）。
7. **警惕自己的记忆**：某本书的版次与页码、某个实验到底测了什么、
   各国安全口径的当前写法，**默认记忆已经过期**，一律现查。
8. **只复述，不抄原文**：**不得**整段翻译或改写他人文字，**不得**搬运他人的图片与表格版式。
   表格必须是自己按本书需要重新组织的；引用他人实验时复述**结论与方法**，不复制表述。
9. **不跨书引用**：仓库里另有《做菜的原理》等书。要用到它讲过的东西
   （美拉德反应、淀粉糊化、蛋白质变性），**在本书里重新讲一遍**，
   并注明"另一本书里也讲过"，**不要写 `../cooking/...` 这种链接**（根 CLAUDE.md §2）。

## 2. 教学法（每章固定结构）

用**中文**写。每章顺序固定为「**概念 → 辨析 → 思考题 → 实操 → 用处 → 依据**」
（`scripts/check_book.py` 会检查小节是否齐全）：

1. **概念**讲解，配机理图（Mermaid）/ 对照表，关键数值带出处；
   **能讲"为什么"就不要只讲"是什么"**；每章结束前要把原理收敛成**一条可迁移的判断规则**。
2. **「常见说法辨析」**表：逐条列出烘焙圈流传的说法，标注证据强度
   （✅ 有共识 / ⚠️ 有争议 / ❌ 明确错误 / 缺乏证据）并给一句理由。
3. 章末**思考题**（数量**按内容而定，不固定 3 道**），紧扣本章，指向答案册（见 §5）。
   题型混用：
   - 普通问答（考原理）；
   - **【案例】题**：给**一份配方**或**一次失败记录**，让读者自己推原因与改法，
     答案册必须给**完整推理链**（"这份配方的目标是什么 → 改动抢走了谁的什么 → 连带要改哪一项"）；
   - **【辨析】题**：给一条流传的说法，让读者判断证据强度并说明怎么验证。
4. **本章实操**，两档：
   - **🅐 零成本版**——**不用烤箱**就能做（把三份配方换算成烘焙百分比并对比、
     读一份商品面包的配料表反推工艺、给一份配方写"改糖 20% 会怎样"的预测）；
   - **🅑 开火版**——标注"**有烤箱时做**"，给**单一变量对照实验**
     （同一份饼干面团分两份，只改糖的用量或形态），并列清所需器具与替代方案。
   实操要给**可填写的记录表**（Markdown 表格或链到 [`docs/forms/`](docs/forms/)）。
5. **🔎「下次烤之前的用处」**：把本章原理翻译成**下次进炉前少犯的那一个错**。
6. **「本章依据」**：本章用到的书/论文/官方页面 + 具体主题或页码范围。

风格：像给同事讲清楚一件事，多用"为什么"，诚实标注反直觉与局限（"诚实说明"）。
**绝不写"这么做一定失败"这类绝对断言**——写"出现 X 时，先怀疑 Y，用 Z 来验证"。

## 3. 单一真源 & 可移植 Markdown（核心原则）

- **内容只存一份**：正文 `docs/`。网页/PDF 都是它的渲染。
- **可移植 Markdown**：必须在 **GitHub 原生渲染 + 普通 Markdown 阅读器 + MkDocs** 三边都能看：
  - 用**脚注 + 引用块**做注释，**不要**用 MkDocs 专有的 `!!! note` admonition；
  - 术语表锚点、思考题跳转都用**显式 HTML 锚点** `<a id="xxx"></a>`（三边通用）；
  - 不用 `--8<--` / `{{#include}}` 这类构建期引用（纯阅读器看不到）；
  - 站内链接用相对路径 `xxx.md#anchor`，**锚点必须真实存在**（校验脚本会查）。
- **可复用的表单**（配方解码表、烘焙记录表）放 `docs/forms/`，
  各章**链接**过去，不复制粘贴。
- **图片版权**：本书**不搬运**他人照片，也不内嵌外链图片。
  要看实物时，正文给**文字判据**（"应该看到什么、摸起来什么手感、闻到什么"）。
  自绘示意图用 Mermaid。

```

  index.md                     # 首页 / 大纲 / 进度
  roadmap.md                   # 七部分学习路线图（活的大纲，改动记进"调整记录"）
  glossary.md                  # 术语表（中文 + 英文 + 解释，每词条前有 <a id> 锚点）
  standards.md                 # 参考书目与出处登记（书/论文/官方页面 + 核对状态）
  forms/                       # 可复用记录表
    index.md
    recipe-decode.md           # 配方解码表（全书核心工具）
    bake-log.md                # 烘焙记录与复盘表
  chapters/NN-partname/        # 每部分一个目录
    00-intro.md                # 该部分开篇导读（每部分都要有）
    NN-name.md                 # 章节，两位数字前缀（全书连续编号）
    summary.md                 # 该部分小结（速查，可选）
    project-PN-xxx.md          # 该部分的实战项目（见 §6）
  qa/NN-name-qa.md             # 思考题答案册（网页可跳转）
```

## 5. 各类文件的具体约定

**章节 `.md`**：小节用 `## N.x 标题`。术语首次出现加脚注 `[^x]`，脚注体链接到术语表
`[术语](../../glossary.md#anchor)`。章末思考题下写跳转链接：
`> 📖 **参考答案**（想清楚再看）：[Q1](../../qa/NN-name-qa.md#q1) · [Q2](...#q2) · …`

**答案册 `docs/qa/NN-name-qa.md`**：**只记「问题 + 正确答案」**，不记读者作答。每题前加锚点
`<a id="q1"></a>`…。案例题答案要给推理链（"目标 → 改动抢走了什么 → 连带影响 → 怎么验证"）。
必须加进 `mkdocs.yml` 的「思考题参考答案」nav（否则 `--strict` 报错）。

**配方与比例的写法（本书特有，硬要求）**：

- 一律写成**烘焙百分比**，并在同一页写明基准，例如"以面粉总量为 100%"；
  校验脚本会检查这句话在不在（见 `scripts/check_book.py` 第 12 项）。
- 配方表至少给三列：**原料 / 烘焙百分比 / 它在这份配方里扮演什么角色**。
- 引用他人配方时**只复述比例与结构**，不抄文字步骤、不搬表格版式。

**温度写法**：一律 `x °C`（可在括号里附 °F），**不许裸写"x 度"**（校验脚本会查）。
涉及烤箱温度时要提醒"**你的烤箱几乎一定不准**"，把炉温当成需要标定的变量。

**出处标注格式**：正文引用著作用统一简称（如 Figoni《How Baking Works》、
Hamelman《Bread》、《Modernist Bread》），并在 `docs/standards.md` 登记
完整书名、作者、版次、对应主题与**核对状态**（✅ 已核对到一手 / ⚠️ 待核对）。
引用官方指引时写机构名 + 页面主题，**并注明"各国口径不同，以当地现行发布为准"**。
标准编号（若出现 `GB xxxxx` / `ISO xxxx`）必须在 `standards.md` 登记过。

**术语表**：新术语加到 `glossary.md` 对应主题下，前置 `<a id="slug"></a>`。
术语要给 **中文 + 英文原词**（烘焙资料大量是英文，读者要能对上）。
`## ` 节标题不许重复（校验脚本会查）。

## 6. 实战项目（重要：不要一章一个）

- 项目**只挂在部分末尾**，同一部分**最多一个**，全书 **5 个**（P1~P5）。
- 项目文档放**所属部分目录**里（`chapters/NN-part/project-PN-xxx.md`），
  nav 排在该部分末尾，**不单独设分区**。
- 项目同样给「🅐 零成本版 / 🅑 开火版」两档，并给交付物模板（表格 / 决策清单）。

## 7. 画图（Mermaid 优先）

> **随时画图**：只要图比文字更清楚，就配图——这是硬要求，别偷懒用纯文字凑。

- **配方结构 / 反应链 / 工艺顺序 / 判断决策树 → Mermaid**：```mermaid 代码块，
  三边都渲染、可 diff。本书最常用：七个角色的争夺关系图、面团从入炉到出炉的时间轴、
  失败现象→原因的排查树、"改一项 → 连带改哪些"的传导图。
- **没有可靠数据来源的量化关系，不要画成"像实测数据"的图**；
  必须画时在标题里写明「示意」，并在图注说明这是定性关系。
- **不要用 matplotlib 画带中文的图**：本机没有中文字体，中文会变方框。
  需要静态图时优先 Mermaid，或写成表格。
- **温度轴图**要标明"这些阈值随体系（含水量、糖、盐、pH、升温速率）漂移"，
  不要画成硬边界——烘焙体系里糖和低水分会把糊化温度推得很高，这一点尤其重要。

## 8. 新增一章的标准流程（照做）

1. 先列本章的知识链条，**确认每个数值有出处**（查不到就改写法，别编）；
2. 写 `docs/chapters/PART/NN-name.md`
   （概念 + Mermaid/表 + 常见说法辨析 + 思考题 + 本章实操 🅐/🅑 + 🔎 + 本章依据）；
3. 写 `docs/qa/NN-name-qa.md`（问题 + 正确答案，q1/q2/… 锚点；案例题给推理链）；
4. 新术语加进 `glossary.md`，新出处加进 `standards.md`，新表格加进 `forms/`；
5. 更新 `mkdocs.yml`（章节 nav + 答案 nav）、`docs/index.md`（进度）、
   `docs/roadmap.md`（状态）；
6. **校验 + 严格构建**（见 §9）全绿后再提交。

## 9. 构建与校验（提交前必做）

```bash
python scripts/check_book.py     # 锚点 / 出处登记 / 章节结构 / 温度写法 / 百分比基准
mkdocs build --strict            # 坏链接或警告即失败（CI 也跑这条）
```

两条全过才提交。仓库级构建（会顺带下发配色与 PWA 生成物）：

```bash
python ../../scripts/build_site.py --only baking
```

⚠️ `docs/assets/palette.css`、`docs/assets/favicon.svg`、`overrides/main.html`
**由 books.yml 下发生成，不要手写、不要手改**。
⚠️ 多人/多 agent 并行时**只能带 `--only baking`**，不带 `--only` 会清空整个 `site/`。

## 10. 提交与发布

- 提交信息中文、说清做了什么 + 为什么；**每完成一块可独立成立的内容就提交**，不要攒到最后。
- push 到 `main` 触发**仓库级** workflow（构建全部书）并发布到 GitHub Pages；
  提交信息加书名前缀，如 `baking: 第 3 章 水`（见根 CLAUDE.md §6）。
- `mkdocs.yml` 配 `site_url` + `repo_url` + `repo_name`；`README.md` 顶部放**在线阅读**链接——
  网页与仓库互相可达。

## 11. 通用约束（来自用户全局规范）

- **不主动写报告文件**（`*.md` 总结、`report_*.json` 等）；结论直接说，除非明确要求导出。
- 需要时间戳用**北京时间**：`TZ='Asia/Shanghai' date '+%Y-%m-%d %H:%M'`。
- **仓库内所有文件禁止出现绝对路径**（尤其带用户名或机器目录布局的）——公开仓库会泄漏个人信息；
  只用相对路径 / 环境变量。聊天里为方便定位可给绝对路径，但**绝不提交进仓库**。
